# Planning Providers

Planning providers turn goals, constraints, and runtime inputs into typed plan documents.

The shared contract uses the `dw.planning.*` provider namespace and the `cap://dw.planning`
capability family.

This family currently includes:

- `core` for shared planning request and plan-document models
- `static` for deterministic config-backed plans
- `llm-outline` for strict JSON-outline planning backed by an injected LLM adapter

Concrete planners build on the shared crate so routing, validation, and later composition tests can
rely on one normalized plan shape.

## Overview

Use the planning family when a runtime needs to turn a user goal into an ordered `PlanDocument`
before execution. Every backend returns the same shared model from `planning/core`:

- `PlanRequest` carries a stable request id, a goal string, and optional structured context
- `PlanDocument` carries a stable plan id, ordered `PlanStep` entries, and provider metadata
- `PlanStep` carries a stable id, a step kind, optional dependencies, and arbitrary JSON payload

Choose a planner by behavior:

- `static` when the plan should come from checked-in config and be fully deterministic
- `llm-outline` when the plan should be generated by an LLM but still validated into the shared
  document model

## Config Reference

Common runtime inputs:

- `request_id`: stable correlation id for logging, reflection, and workspace writes
- `goal`: human-readable planning goal
- `context`: optional machine-readable inputs used for interpolation or prompting

Planner-specific configuration:

- `planning/static`
  - `plan`: required `PlanDocument` returned by the provider
  - `interpolate_variables`: when `true`, `{{request_id}}`, `{{goal}}`, and object keys from
    `PlanRequest.context` are expanded inside ids, metadata, dependencies, and payload values
- `planning/llm-outline`
  - `adapter`: injected LLM client implementing the backend bridge
  - `system_prompt`: fixed planning instructions
  - `max_steps`: hard cap on accepted step count
  - `allowed_step_kinds`: optional allow-list for emitted step kinds
  - `retry_invalid_output`: whether one validator-guided retry is allowed

## Example Manifest Snippet

```json
{
  "providers": [
    {
      "id": "planner-static",
      "type": "dw.planning.static",
      "capabilities": ["cap://dw.planning.plan"],
      "component": {
        "ref": "oci://ghcr.io/greenticai/packs/dw/planning/static-pack:0.5.4"
      },
      "config": {
        "interpolate_variables": false
      }
    }
  ]
}
```

## Expected Runtime Behavior

- Planning runs before delegation, workspace writes, and most reflection flows.
- Returned plans are validated for empty ids, duplicate step ids, self-dependencies, and unknown
  dependencies.
- Step `kind` values are expected to remain stable because later routing depends on them.
- Static planning should be deterministic for the same config and request.
- LLM-outline planning may vary internally, but accepted output is normalized into the same typed
  plan document before it leaves the provider boundary.

## Troubleshooting

- If planning fails with `duplicate plan step id`, the configured or generated plan emitted the
  same step id more than once.
- If planning fails with `depends on unknown step`, a step references an id that is not present in
  the final ordered plan.
- If interpolation leaves raw `{{name}}` placeholders behind, the matching key was not present in
  `PlanRequest.context`, `request_id`, or `goal`.
- If `llm-outline` rejects output repeatedly, tighten the prompt, reduce the allowed step kinds, or
  lower `max_steps` so the model has a narrower contract to satisfy.
